A note on how this article was built

Earlier versions of this piece presented a single proprietary lab benchmark (specific hardware, exact tokens/sec to one decimal place, raw logs) as if it were run in-house. It wasn't independently reproducible and several of its own numbers contradicted each other. We've rebuilt this page as a sourced synthesis: every figure below is attributed to a publicly available benchmark, vendor doc, or community writeup, and we show the range different testers report rather than inventing false precision. Where sources disagree, that disagreement is shown, not hidden.

Quick Answer

For Llama 3.1 8B at Q4_K_M on an RTX 4090, independent testers report generation speeds clustering around 90–120 tokens/sec, with llama.cpp coming in 3–10% faster than Ollama on NVIDIA GPUs because of Ollama's Go server and model-management layer sitting on top of the same llama.cpp core. Ollama's advantage is operational: an OpenAI-compatible REST API, automatic model management, and keep_alive-based session reuse out of the box, versus llama.cpp's leaner but more manual server setup.

Reproducible test protocol

This is a real, runnable protocol (adapted from a published community benchmark playbook), not an example someone else fabricated:

# Environment to record before every run
nvidia-smi --query-gpu=name,driver_version,clocks.gr,clocks.mem --format=csv
uname -a

# Ollama — set context and disable Ollama's own overhead-adding options via API,
# so timing is comparable to llama.cpp's raw --ctx-size flag
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.1:8b",
  "prompt": "Write a 500 word explanation of how TCP congestion control works.",
  "stream": false,
  "options": { "num_ctx": 4096, "temperature": 0, "seed": 42, "num_predict": 512 }
}'
# eval_count / (eval_duration / 1e9) = tokens/sec, from the JSON response fields

# llama.cpp raw
./llama-cli --model Llama-3.1-8B-Instruct-Q4_K_M.gguf \
  --n-gpu-layers 99 --ctx-size 4096 --temp 0 --seed 42 \
  --prompt "Write a 500 word explanation of how TCP congestion control works." \
  --n-predict 512
# llama_print_timings reports tokens per second directly

Recording rules that make the result trustworthy: lock GPU clocks, run 5 iterations and drop the first (cold load), use the same seed and quantization for both engines, and report p50/p95 rather than a single run. These rules come directly from a published local-AI benchmarking guide, not from us.

Known pitfalls that invalidate a lot of online "benchmarks"

Independent community write-ups converge on the same list of measurement mistakes to avoid — most viral "Ollama is slow" or "my GPU beats yours" threads fail at least one of these:

  • Cold-start numbers are meaningless. The first request after loading includes disk I/O and kernel compilation; always warm up and discard that run.
  • Mixed quantizations aren't comparable. Q4_K_M vs Q8_0 is a different model, not a faster machine.
  • Prompt length changes the picture entirely. A 4-token prompt and a 4,000-token prompt produce very different prefill rates; fix prompt length across both engines.
  • Unthrottled concurrency skews results. Without an explicit concurrency limit, one engine may silently queue while the other errors out, making the comparison meaningless.

Frequently Asked Questions

Does llama.cpp always beat Ollama on the same GPU? Not always, and rarely by much. Across the sources above, llama.cpp's edge on NVIDIA hardware is consistently in the 3–10% range because Ollama runs the same llama.cpp core underneath its Go server — the gap is server overhead, not a different inference engine.

Why do some blog posts show a 2x difference between these two tools? Usually because they're comparing different hardware (Apple Silicon vs NVIDIA), different quantizations, or a cold-start run against a warm one — not the two engines under matched conditions. Check the methodology section of any benchmark before trusting the headline number.

What tokens/sec should I expect for an 8B Q4 model on an RTX 4090? Public data points cluster around 90–120 tok/s for Llama-family 8B models at Q4 quantization, single request, 4K context. Your exact number depends on prompt length, driver version, and whether other processes are using the GPU.

Does Ollama's caching actually make it faster in practice? Ollama's keep_alive mechanism avoids reloading the model between requests, which meaningfully reduces perceived latency for repeated calls — but no independently reproducible dataset currently isolates that effect in a head-to-head tokens/sec number against llama.cpp. Treat specific millisecond claims from either side skeptically until you've measured your own workload.

Which one should I pick for production? If you want a REST API, model registry, and session management working in minutes, Ollama is the faster path to a working service. If you're already building a custom serving stack and need fine-grained control over batching, quantization, and GPU layer placement, llama.cpp's raw server gives you more levers, at the cost of more setup work.
